# 小红书下载器 · 设计文档

日期：2026-10-24
状态：V1 已实现并通过端到端验证

---

## 1. 意图与为什么

用户在小红书网页上看到一篇笔记或一个博主的主页时，想要的是**把内容原样存到本地**：
视频要能播、图片要原图、文件名要能认出是哪篇、批量时不能一个一个点。

现有同类插件的共同问题（来自 Edge / Chrome 商店的真实评论与竞品截图）：

- 识别不准，页面上明明有 9 张图，只给出 2 张
- 批量下载到一半静默失败，用户不知道哪些失败了
- 命名混乱，下载完分不清哪个是哪个
- 反复要求「登录」「授权」，体验割裂

本产品的判断：**技术上真正难的只有「拿到稳定直链」，其余全是交互与诚实的工程。**
所以把 80% 的力气花在直链推导、失败可见、命名可预期上，而不是堆功能。

## 2. 目标 / 非目标 / 反目标

**目标**

1. 在笔记详情页自动识别全部视频与图片，给出可复制的直链与下载按钮
2. 点击下载时有真实的进度反馈（字节级），完成后明确告知结果
3. 在用户主页一键扫描该账号的全部笔记，分类展示（视频 / 图集），支持勾选、全选、反选、筛选
4. 下载内容是**原始画质**：图片走原图 CDN，视频走免签名直链
5. 文件名可预期：默认落盘为 `小红书下载/作者/标题/序号.扩展名`
6. 失败必须可见、可重试，且说清原因

**非目标**

- 不做无水印视频解析（小红书 Web 端视频本身就没有水印，不需要）
- 不做评论 / 点赞数导出
- 不做云端同步、多端管理
- 不绕过登录：游客态拿不到的内容，我们如实告诉用户「需要登录」

**反目标（做到就算失败）**

- 静默失败：下载了 0 个文件却提示「已完成」
- 拿预览图（小图 webp）冒充原图
- 用列表里的封面冒充视频
- 靠猜测拼 URL（签名会过期，拼错就是 403）

## 3. 约束

### 3.1 浏览器约束（实测 + Chromium 源码确认）

| 约束 | 结论 | 依据 |
|---|---|---|
| Chrome 137+ 正式版禁用 `--load-extension` | 自动化测试必须用 Chrome for Testing | 实测 |
| `chrome.downloads.onChanged` 的 delta **没有** `bytesReceived` | 进度必须轮询 `chrome.downloads.search({id})` | Chromium 源码 |
| `chrome.downloads.download({filename})` 遇到非法字符 → **整个调用失败**（`Invalid filename`），不是替换成 `_` | 文件名必须在调用前就合法 | `downloads_api.cc` |
| 非法字符集合跨平台统一：`: * ? " < > \| \` + `\p{Cc}` + `\p{Cf}` | 清洗规则以实测为准（见 3.1.1） | `base/i18n/file_util_icu.cc` + 实测 |
| 扩展发起的下载豁免「允许多个文件下载」提示 | 批量下载不会弹权限气泡 | `download_request_limiter.cc` |
| `chrome.downloads.download()` **不需要** host_permissions | 直链交给浏览器下载器，不走扩展的 CORS | `_api_features.json` |
| `conflictAction: "prompt"` 在桌面端会弹原生模态框 | 一律用 `uniquify` | 实测 |
| **DNR 规则对 SW 发起的下载请求完全无效** | 同一条规则对页面请求生效、对下载请求不生效 | 实测（`scripts/probe-dnr.mjs`） |
| `chrome.downloads.download({headers})` 无法设置 Referer | `net::HttpUtil::IsSafeHeader` 硬拒 | Chromium 源码 |

#### 3.1.1 文件名的完整规则（逐字符实测）

`scripts/probe-filenames.mjs` 在真实 Chrome 上逐个字符、逐个扩展名试过
`chrome.downloads.download({filename})`，得到的拒绝清单：

| 会被拒 | 细节 |
|---|---|
| `: * ? " < > \| \` | 加上控制字符（`\p{Cc}`，含 tab/换行）与格式字符（`\p{Cf}`，含零宽空格） |
| 以 `.` 开头的**路径段** | `.隐藏文件.jpg`、`.foo.bar.jpg`、`a/.b/c.jpg` 全被拒 |
| 以 `.` 或空格结尾的路径段 | `文件.`、`文件 ` 被拒；`文件 .jpg` 可用（空格不在段首尾） |
| 保留设备名 | `con` `prn` `aux` `nul` `com1-9` `lpt1-9` `clock$`；判据是**第一个点之前**那段 —— `con.jpg` 被拒而 `file.con.jpg` 可用 |
| Shell 集成扩展名 | `.url` `.lnk` `.scf` `.local`（大小写不敏感）；判据是**最后一个点之后**的扩展名 —— `foo.url` 被拒而 `foo.url.jpg` 可用 |
| 空文件名、`.`、`..` | |

> 流传的清单里还有 `.ade` / `.adp`，**实测这两个是可用的**，所以不拦。
> `COM0` / `COM10` / `LPT0` 不在保留名单里，实测可用。

**实现要点**：清洗分「词干」与「扩展名」两层，规则不同；
**截断只切词干** —— 直接截断整串会把 `.jpg` 砍成 `.jp`，用户拿到的文件打不开。

### 3.2 小红书侧约束（全部为线上实测结论）

| 事实 | 影响 |
|---|---|
| 图片原图 = `https://sns-img-qc.xhscdn.com/{fileId}`；路径上一段若是 32 位 hex 签名目录则只保留 `fileId`，否则保留业务目录段 | 直接剥 `!suffix` 会 403（签名与后缀绑定） |
| `?imageView2/format/jpeg` 得到同分辨率 JPEG，扩展名稳定 | 默认给 JPG，原图模式给原格式 |
| 视频直链在 `note.video.media.stream` 下，**分桶名随版本变**（见过 `EF4/EF5/EF6/EF7`，也见过 `h264/h265/h266/av1`） | 必须遍历所有桶，不能写死 key |
| 视频是 progressive mp4，**没有 m3u8** | 不需要 HLS 合并 |
| `backupUrls[0]`（`sns-bak-v1.xhscdn.com`）**不带签名**，最稳；`masterUrl` 带 `?sign=&t=` 会过期 | 优先用 backup 地址 |
| `imageList[i].url` 恒为空串 | 用 `urlDefault` 或 `infoList[WB_DFT].url` |
| `__INITIAL_STATE__` 里部分字段是 Vue ref，需解包 | 提取层统一 `unref()` |
| `noteDetailMap` 可能出现字面 key `"undefined"` | 跳过 |
| `xsec_token` 形如 `{{SECRET_xxx}}` 是**有效格式**，服务端接受 | 缺失才会 404 |
| **有一部分笔记的 `title` 是空字符串**，真正的标题在 `desc` 里（推荐流 `displayTitle` 也有） | 标题要有兜底链，见 4.4.2 |
| `user.notes` 是「5 个 tab × 每 tab 一个数组」的**双层结构**，每条 item 的 `id` 为空串、真实 id 在 `noteCard.noteId` | 提取层按双层结构处理 |
| **游客态下主页不返回笔记 id**：DOM 里链接只有 `/explore/`，`user_posted` 返回的 `note_id` 是空串，且限 10 条 | 主页完整扫描**必须登录**；游客态要如实告知并给登录入口 |
| 主页滚动容器是 `.reds-lock-scroll`，不是 window | 滚 window 无效 |
| 笔记页是**服务端渲染**的，`__INITIAL_STATE__` 内联在 HTML 里 | 隐藏 iframe 加载笔记页，**实测 370ms** 就能读到状态 |
| `window._webmsxyw(url, payload)` 返回 `{X-s, X-t}`（签名头），但只带这两个头调 `/api/sns/web/v1/feed` 会返回 `500 create invoker failed` | 签名 API 需要完整反爬头（`mnsv2` / `a1` / `X-S-Common`），**不采用** |
| 当前图片与视频直链**不校验 Referer**（带/不带都是 200） | 不需要为 Referer 做任何事 |
| `rednote.com`（国际版）全部页面强制跳登录 | 无法在游客态验证，**暂不支持** |

### 3.3 架构约束

- Manifest V3：Service Worker 30 秒空闲即终止，**所有状态必须可持久化**
- content script 在**隔离世界**，读不到页面的 `window.__INITIAL_STATE__`
- 页面状态是站点自己的运行时对象，**必须容忍字段随版本变动**

## 4. 架构决策

### 4.1 双 content script + postMessage 桥接

隔离世界拿不到页面状态，所以：

- `page-hook.js` 以 `world: "MAIN"` 注入，作为页面数据的代理，提供 RPC
- `content.js` 在隔离世界，负责 UI 与业务
- 通道密钥写在 `<html data-rednote-channel>` 上（DOM 跨 world 共享），用于校验消息来源

**两个必须记住的坑**（都真实踩过）：

1. `window.postMessage` 会把消息投递给同一个 window 上的**所有**监听器，包括发送方自己。
   两侧都必须忽略「自己发出的请求」：
   - MAIN world 侧：没有 `method` 的一律不处理。否则「响应 → 当成请求 → 再响应」会形成**无限消息风暴**，把真正的响应挤掉。
   - 隔离世界侧：没有 `ok` 字段的一律不处理。否则请求会被自己 reject，报出莫名其妙的错误。
2. 站点在 `document_start` 之后才写入 `__INITIAL_STATE__`，DOM 也是之后才渲染。
   content script 跑在 `document_start`，**第一次检测必然失败**。因此：
   - page-hook 轮询到状态就绪后，在 `<html>` 上打 `data-rednote-state="1"` 标记
   - content script 持续重试检测（最长 12s），状态就绪标记到达时立即再跑一次
   - DOM 兜底是**最后手段**，不能因为 DOM 先渲染出来就抢跑（DOM 里的视频地址常是 `blob:`，下载不了）

### 4.2 数据来源优先级

`页面状态 (__INITIAL_STATE__)` → `站点 API 响应（拦截 fetch/XHR）` → `DOM`

主页扫描时三路并行收集再合并去重。页面状态优先，因为它给的直链最稳。

### 4.2.1 主页里的单篇笔记怎么解析

主页只给笔记**卡片**（id、封面、类型），媒体资源得另外取。三条路按代价排序：

| 路径 | 代价 | 说明 |
|---|---|---|
| 页面状态里已有这篇笔记 | 0ms | 命中就是直接用（**必须带媒体**，空壳不算命中） |
| **隐藏 iframe 加载真实笔记页** | ~370ms（实测） | **主路**：读页面渲染后的状态 |
| 抓笔记页的 HTML | ~1 次网络请求 | 快路：只有自证过与页面一致才准接手 |
| 站点签名 API | 未采用 | 见下 |

**主路是隐藏 iframe —— 也就是 1.0.0 的做法（2026-10-25 改回来）**：
iframe 读到的是「用户眼睛看到的那份数据」，页面脚本跑完、XHR 回来之后的状态；
抓 HTML 读到的是服务端渲染出来的那一份，两份**不一定一样**
（地址可能不同、清晰度可能不同、签名可能更早过期）。
用户反馈「现在的下载效果还不如 1.0.0」—— 1.0.0 走的就是 iframe，那就让 iframe 说了算。

**为什么 v1.3.0 的「抓 HTML 当主路」是错的**（两层原因，缺一不可）：

1. **快路在真站点上基本是死的。** 站点内联的状态不是合法 JSON（JavaScript 对象字面量，
   带 `undefined`），而且笔记详情**根本不在 SSR 里**（游客态实测 `noteDetailMap` 是空的，
   详情由页面 JS 用 XHR 拉）。于是每条笔记都白抓一个完整页面。
2. **白抓的请求会抢连接池。** 浏览器每个域名只有 6 条连接，抓 HTML 和 iframe 加载
   走的是同一个站点同一个池子。多打一遍等于把站点压力翻倍，iframe 反而被挤掉 ——
   表现就是「解析经常失败」。

**快路要自己证明自己可信才准用（2026-10-25）**：
第一条**带视频**的笔记两条路都跑一遍，把**最终要下载的那个地址**逐条比对
（视频优先用 `backupUrls[0]`，因为那才是实际下下来的那个）：

- 完全一致 → SSR 里那份和页面渲染那份是同一份东西，之后允许快路接手
  （几百条笔记就不用开几百个 iframe）。
- 不一致 → 整场都用页面的结果。宁可慢，也不能下到不一样的东西。

**只拿带视频的笔记去自证**：视频直链最容易出差别（页面用 backup 地址，
SSR 里可能只有 master 地址）；拿一条纯图片笔记去自证，证明不了视频那条路也靠谱。

自证只做一次，整场共享一个结论（并发解析时只允许一个自证在飞）；
抓 HTML 抓不到东西时立刻认输，后面一条笔记都不再白抓。

**抠 `__INITIAL_STATE__` 的两个坑（2026-10-24 实测）**：

1. **它不是合法 JSON。** 站点的状态是 JavaScript 对象字面量，里面有 `undefined`
   （实测：登录页 23 处、发现页 29 处）。`JSON.parse` 必然抛错 ——
   第一版快路就是这么写的，于是它在真站点上 100% 失效、每条笔记都白抓一个页面。
   现在按括号配平扫描出对象文本，把 `undefined` / `NaN` / `Infinity`
   换成 `null` 之后才解析（`parseJsLiteral`）。
2. **笔记详情可能不在 SSR 里。** 游客态下笔记页 SSR 出来的 `note.noteDetailMap` 是空的 ——
   详情是页面 JS 跑起来之后用 XHR 拉的。这种站点上快路是白费的，
   现在会**认出来**（状态里连详情块都没有）并立刻改走 iframe。
   （游客态访问笔记页还会被重定向到 `/login`，未登录时无法验证登录后的 SSR 形状。）

**时间预算**：抓 HTML 最多 5s（`AbortController` 自己掐表，请求卡住时不能把预算吃光），
隐藏 iframe 最多 10s（笔记已经出现但媒体还没补上时再多等 4s），
整条链路 20s 封顶。桥接层给这个调用单独放宽到 26s ——
用默认的 15s 会在预算用完之前先把调用砍掉，界面上就显示成「解析失败」。

**空壳不算成功**：页面的状态是一点点填进来的（一开始只有 id 和标题，视频直链后面才补上），
早一步返回就是「解析成功但一个视频都没有」—— 不报错、不重试、也下不出文件。
现在这种情况卡片上写「**未取到资源**」：既不装作成功（骗人），
也不说成「解析失败」（那是在怪插件，明明是这条笔记没资源）。这个提示不被赞数盖住。

**为什么不用签名 API**：页面的 `window._webmsxyw(url, payload)` 确实能生成 `X-s` / `X-t`，
但只带这两个头去调 `/api/sns/web/v1/feed` 会返回 `500 create invoker failed`。
真正能用还要 `mnsv2`、`a1`、`X-S-Common` 一整套反爬头，而站点改一次签名逻辑就得重做一遍。
读渲染结果不依赖任何反爬内部实现，反而更稳。

**并发**：批量解析并发 4 条。每条卡片实时显示「解析中 / 解析失败」，
失败必须留在界面上并计入汇总 —— 竞品里最常见的槽点就是「下了 10 张漏了 3 张」却没人告诉你。

### 4.2.2 笔记 id 必须精确匹配

`extractNoteFromState(state, noteId)` 传了 `noteId` 就**必须精确命中**，命中不了返回 `null`。

早期版本这里会「命中不了就退回状态里的任意一条」。后果是：批量下载时把**别的笔记**
当成了用户勾选的那条，静默下错内容 —— 这比直接失败糟糕得多。

笔记详情页是例外：URL 里的 id 和状态里的对不上时（站点重定向过），
退回「页面当前这条」是对的，所以那一路显式传 `loose: true`。

### 4.3 下载层

- **两种方式**：`browser`（默认，逐个文件交给 `chrome.downloads`）/
  `zip`（整批打成一个包再交给 `chrome.downloads`），由设置切换；
  两条路共用同一套队列、重试、统计、广播
- 队列在 Service Worker 里，状态存 `chrome.storage.session`（SW 被杀后能恢复）
- 进度**一次查询覆盖所有在跑的下载**，只在有活动任务时轮询
- 失败原因回传到 UI 并支持单项重试

**进度刷新必须做成「一次查询，一批下载」**（详见 4.3.1）：
`downloads.search` 的 `id` 不接受数组，每个在跑的下载各查一次的话，
查询量 = 事件数 × 并发数，几十个文件就能把浏览器拖慢。

**下载失败必须能自愈**，否则用户看到的就是「转圈转到天荒地老」：

| 情况 | 处理 |
|---|---|
| 网络瞬断（`NETWORK_FAILED` / `NETWORK_TIMEOUT` / `SERVER_FAILED` 等 6 类） | 指数退避自动重试（1s → 2s），最多 2 次；状态是 `retrying`，界面显示「正在重试」而不是失败 |
| 浏览器报告完成但 `fileSize === 0` | **判为失败** —— 否则用户以为下好了，硬盘上什么都没有 |
| SW 被 Chrome 杀掉（空闲 30 秒）后重新拉起 | 用 `downloads.search({id})` 对账：浏览器还认得的继续跟，查无的标失败 |
| 用户主动取消 | 标为「已取消」，不计入失败数 |

#### 4.3.1 批量下载的性能：查询要合并，渲染要打补丁

用户反馈「批量下载时卡顿」。实测（`scripts/probe-perf.mjs`，12 条笔记 / 并发 3）
确认了两个放大点，都不是「下载本身慢」，是**周边动作放大了**：

| 指标 | 改之前 | 改之后 |
|---|---|---|
| `chrome.downloads.search` 次数 | 96（24.8 次/秒） | 12（3.6 次/秒） |
| 往页面推的进度消息 | 26 条 / 58 KB | 9 条 / 11 KB |
| 卡片重建次数 | 300 | 12 |
| 缩略图重建次数 | 300 | 12 |

**根因一：查询次数 = 事件数 × 并发数。**
`downloads.onChanged` 每来一个事件就触发一次「全量查询」，而全量查询是对
每个在跑的下载各调一次 `search`。事件本身很密（每个文件至少 filename + state 两条），
于是并发 3 时一秒能打出去近 50 次 `search`。

改法：
- `search` 的 `id` **不接受数组**（传数组直接抛 `TypeError`，实测过），
  所以改成「取最近 N 条 + 按需兜底」：批量下载总是最近启动的那批，
  落进最近 N 条里；万一被用户同时下载的别的东西挤出去，再按 id 补查那几条
- 下载事件不再直接触发查询，只负责**唤醒**；唤醒与兜底节拍共用一个定时器，
  密集事件自然合并成一次查询
- 查询节拍 300ms，事件唤醒最小间隔 250ms

**根因二：进度每变一次就把整个面板重画一遍。**
主页一次可能有几十张卡片，重画 = `body.innerHTML = ''` 再重建整张网格，
其中每个 `<img>` 都要重新解码 —— 这才是页面真正卡住的原因
（MutationObserver 数不到这些节点：卡片是在游离节点里建好才挂上去的，
只看「挂上去的那一块」才量得出来）。

改法：进度更新只**打补丁** —— 笔记页改那一行、主页改那一张卡，
缩略图一个字节都不碰。整块渲染和增量更新共用同一份绘制函数，
避免两份逻辑各写各的、日后走样。

**顺带修掉的两个真问题**：
- `poll()` 没有重入保护，两个查询同时看到同一条 `complete` 记录会把完成数**数重**
- 状态快照每变一次就全量写一次 `storage.session`，写入量 O(文件数²)，
  几百个文件的批量能写掉几十兆，还会撞上 storage 的写配额（每分钟 120 次）——
  配额一爆快照就停在旧版本，SW 被杀之后恢复出来的状态是错的

**权限收敛**：`declarativeNetRequestWithHostAccess` 曾用于给 xhscdn 补 Referer，
但实测 DNR 规则**对 SW 发起的下载请求无效**，那条规则是死代码，连带权限一起删。
`https://*.xhscdn.com/*` 的 host 权限同样删掉（不需要）。
最终只申请 `downloads` + `storage` 两个权限 —— 权限越少，商店审核越顺、用户越敢装。

> 自研下载引擎上线后，权限清单**没有变**：CDN 回 `access-control-allow-origin: *`，
> 所以扩展读媒体字节不需要任何 host 权限；`downloads` 权限保留下来是因为
> `browser` 那条备选路径还要用它。

#### 4.3.2 打包：把 300 个文件变成 1 个（2026-10 改）

**决策**：默认方式是 **Chrome 的默认下载模式**（一个文件一条下载记录）。
另外提供**打包模式**：整批打成一个 zip，再交给 Chrome 下载 —— 下载栏里仍然是
一条正常记录、一个文件，双击解开。

**这一节的前身是「扩展自己写盘」，已删除。**
v1.2.0 把落盘从 Chrome 手里接过来，理由是「浏览器里不会留下下载记录、下载栏不占屏」。
实测下来体验反而更差：多了一次「选文件夹」的操作与一次授权，
而且用户反馈「下载超过一两百个文件后系统变得很卡，甚至报错」。
根因不是自己写盘写得慢，而是**文件数量本身** ——
300 个文件就是 300 次落盘、300 条下载记录，机器要处理 300 次文件事件。

**所以问题不是「谁来写」，是「要落几个文件」。**
打包模式直接把数量从 300 降到 1，量级上的差别，不是常数因子。

**实测（`scripts/probe-scale.mjs`，本地假站点，300 个视频）**：

| | 浏览器下载 | 打包成 zip |
|---|---|---|
| Chrome 里的下载记录 | 300 条 | **1 条** |
| 磁盘上多了几个文件 | 300 个 | **1 个** |
| 总耗时 | 31.4 秒 | **0.5 秒** |
| 并发提到 10 | 37.7 秒（不更快） | — |
| 解析 300 条笔记用的隐藏 iframe | 4 | 4 |
| `storage.session` 写盘 | 5 次 / 0.51 MB | 5 次 / 0.51 MB |

**解析阶段有两种形态，量级差别很大（同样 300 条笔记）**：

| 解析走哪条路 | 隐藏 iframe | 解析 + 打包下载 | 失败 |
|---|---|---|---|
| 快路自证通过（SSR 里带详情） | 4 个 | **0.5 秒** | 0 |
| 最坏情况（自证不通过，整场走页面） | 300 个（同时最多 4 个） | 40.7 秒 | 0 |

最坏情况对应「SSR 里没有笔记详情」的站点形态（游客态实测如此，登录态还没验证过）——
所以真站点上 300 条笔记可能要等四十秒，是**正常的**，不是卡死。
（v1.3.0 的「抓 HTML 当主路」在同样场景下是 148 秒：每条笔记都白抓一个页面，
那些请求还跟 iframe 抢同一个连接池。现在白抓的只剩每场一次的自证。）

**为什么是「整批一个包」而不是「十个一个包」**：
十个一个包只是把 300 变成 30 —— 机器照样要处理 30 次落盘，
而标准 ZIP 单文件上限 4GB，几百个大视频很容易超。
真要超了，扩展会**按 2GB 一个包自动切开**（文件名带 `-1` `-2`），
这是兜底，不是默认策略。

**为什么不压缩**：我们要打包的是 JPEG / MP4，本身就已经压缩过，
再 deflate 一遍几乎压不动（通常还更大），只是白白烧 CPU、拖慢速度。
ZIP 在这里的价值是「1 个文件代替 300 个」，不是「把文件变小」。
所以用 **STORE（method 0）**。

**架构上的落点 —— 为什么必须开后台页面**：

```
用户点下载
   ↓
Service Worker：settings.downloadMode === 'zip'？
   ├─ 否 → 走 chrome.downloads（一个文件一条下载）
   └─ 是 → ensureOffscreen() → 发 ZIP_START 给后台页面
            ├─ 后台页面：并行 fetch 收字节 → 按勾选顺序串行写进 OPFS
            ├─ 后台页面：造 blob 地址 → 报 ZIP_PACKS_READY
            ├─ Service Worker：chrome.downloads.download(blob 地址)
            └─ 下载完成 → 标记全部条目完成 → ZIP_CLEANUP 删掉临时包
```

三条硬约束决定了「打包不能在 Service Worker 里做」：

1. **MV3 的 Service Worker 空闲 30 秒就被浏览器杀掉** —— 几百个文件的活儿跑不完。
2. **`URL.createObjectURL` 在 Service Worker 里根本不存在**（实测：
   `URL.createObjectURL is not a function`）—— blob 地址造不出来。
3. **后台页面里没有 `chrome.downloads`、也没有 `chrome.storage`**（实测都是 `undefined`）——
   只有 `chrome.runtime` 可用。所以两边分工：
   后台页面造 blob 地址，Service Worker 发下载，通过消息接力。

**包先写进 OPFS（扩展的私有文件系统）**：几百兆的包不会把内存吃满，
也不会占着用户的磁盘；下完立刻删掉。OPFS 在 Service Worker 与后台页面里都能读写
（实测 `navigator.storage.getDirectory()` 在 SW 里可用）。

**内存占用**：下载是并行的（网络是瓶颈），但 ZIP 是顺序结构，写入必须串行。
所以每个下载线程先把文件收进内存，写入线程按顺序取走 ——
峰值内存 ≈ 并发数 × 单个文件大小。

**三个必须踩过才写出来的坑**：

1. **写入器必须支持 `seek()`**。CRC 和大小要等数据写完才知道，
   所以先写占位的本地头，写完数据再回头补 —— 内存版 sink 一开始忽略了 `seek()`，
   结果中央目录位置全错、包解不开（而且是「看起来下载成功了」的坏包）。
2. **下载线程与写入线程之间要有「关队列」的信号**。顺序队列的 `take()`
   在「还没有下一个」时会一直等 —— 下载线程全部结束后必须显式关队列，
   写入线程才知道可以收工。少了这一步，包永远打不完（实测：任务卡在 99%）。
3. **每个任务用自己的临时目录**。打包开头要清掉目录里的残骸（上次崩了留下的），
   两个任务同时跑就会互相删文件 —— 所以目录名带上任务 id：`pack-<taskId>`。

**ZIP 格式的取舍**：本地头 + 数据 + 中央目录 + 结束记录，
标准做法（不用「数据描述符」那个变通），任何解压工具都能读。
文件名走 UTF-8（通用位标记 bit 11），中文名在 macOS / Windows / Info-ZIP 上都能正确还原
（实测用 Python `zipfile` 与 macOS `ditto -x -k` 交叉验证）。

**包内路径**：跟「按笔记」保存结构一致 —— `作者/标题/1.mp4`。
根文件夹不进包内（包本来就落在浏览器的下载目录里）。

**如实记录的限制**：

- **打包模式要多等一会儿**：文件要先收齐再打成包，界面上的进度条走的是「打包进度」，
  不是「下载进度」—— 包没打好之前，磁盘上还没有东西。
- **单文件重试会单独打一个 `-补` 的小包**，不影响已经下好的那个包。
- **打包模式下没有断点续传**：中途失败只能整个重下（`createWritable` 是「临时文件 + 提交」，
  数据只在 `close()` 时落盘）。
- **后台页面被浏览器回收了任务就没了**（扩展重载、浏览器退出）——
  SW 重启时对账发现后台页面不在，就把在途条目标失败让用户重试。

### 4.4 命名规则

默认落盘：`小红书下载/{作者}/{标题}/{序号}.{扩展名}`

- 目录已经包含作者与标题，文件名就用序号 —— 避免 `作者_标题_1.jpg` 出现在 `作者/标题/` 里的冗余
- 视频与图片统一连续编号（1 起）：`1.mp4`、`2.jpg`、`3.jpg`
- 模板里没写 `{ext}` 时**自动补上扩展名**（否则文件打不开）
- 文件名清洗严格对齐 Chromium 的规则（见 3.1.1），并在设置页实时预览完整路径
- **文件名在下载时才算，不在识别时定死**：文件名依赖设置（模板、保存结构），
  用户随时可能改，识别时定死就会出现「面板显示旧名字、落盘是新名字」
- 模板里某个变量为空时，连同紧邻的一个分隔符一起去掉 ——
  否则 `{author}_{title}_{index}` 遇到空标题会变成 `小美__1.mp4`

### 4.4.1 保存结构：按笔记 / 按作者 / 全部平铺

**要解决的问题**：每篇笔记一个 `作者/标题/` 的嵌套目录，对「我就想把这个博主的视频
全存一处」的场景不直观 —— 用户要在三层目录里翻。
反过来，全部平铺在主文件夹也不对 —— 不同作者的内容混在一个目录里，
用户还是认不出哪个文件是谁的。

**三种结构**（`saveStructure`），本质是「目录有几层」：

| 结构 | 落盘 | 谁承担身份 |
|---|---|---|
| `perNote` 按笔记 | `小红书下载/小美/周末京都/1.mp4` | 目录（作者 + 标题） |
| `perAuthor` 按作者 | `小红书下载/小美/周末京都_1.mp4` | 目录分作者，文件名分笔记 |
| `flat` 全部平铺 | `小红书下载/小美_周末京都_1.mp4` | 全靠文件名 |

**为什么各配一套命名模板**
（`fileNameTemplate` / `perAuthorFileNameTemplate` / `flatFileNameTemplate`）：
三种结构对模板的要求根本不同 —— 按笔记时目录里已经有作者和标题，
文件名用序号就够；按作者时标题得进文件名，否则同一个作者的多篇笔记
会撞成 `1.jpg`；全部平铺时文件名是**唯一**的身份标识，必须带作者与标题。
共用一套模板的话，要么出现冗余，要么一堆 `1.mp4`
（Chrome 只能给你加成 `1 (1).mp4`）。三套模板换来的是「每种结构开箱即用」。

设置页只显示当前结构对应的那一套模板（带标签说明是哪套），
切换结构时同步切换，避免几套模板互相覆盖。

**状态存在设置里**：换页面、关掉面板再打开都还认这个偏好。
面板工具条第三行（笔记页第二行）也提供同一组分段控件 —— 「下载时可选择」。
三个页签统一用「按什么分组」的角度命名（按笔记 / 按作者 / 全部平铺），
面板只有 360px 宽，长文案放不下。

**兜底**：全部平铺模式下，若模板里既没有 `{title}` 也没有 `{author}`，
设置页会明确提示「只用序号会分不清不同笔记」。

**旧设置迁移**：老版本只有一个「按笔记建子文件夹」开关，
`folderByNote: false` 迁到 `flat`，其余迁到 `perNote` —— 不让老用户升级后目录结构突变。

### 4.4.2 标题识别：绝不用编号冒充标题

**实测结论（2026-10）**：小红书**有一部分笔记的 `title` 字段是空字符串**，
真正的标题被放在 `desc` 里（推荐流的 `displayTitle` 同时也有正确标题）。
这类笔记在推荐流里占比不低。

**曾经的写法**：`title = note.title || note.noteId` —— 标题为空时拿笔记编号顶上。
后果是文件名变成一串编号（`小美_6ab98ed9000000001500e7b7_1.mp4`），
用户完全认不出下的是哪条内容。**这不是「取错了字段」，是缺少兜底策略。**

**现在的取值链**（`extractNote`）：

```
raw.title → raw.displayTitle → desc 首行（去掉 #话题 与 [表情]，过长则放弃）
```

主页批量下载还有一路更可靠的来源：列表卡片的 `displayTitle`。
`resolveNoteDetail` 会把「有效标题」算一次，同时喂给面板显示与文件命名 ——
**面板显示什么，文件名就是什么**（以前两者各算各的，才会出现显示正常、文件名是编号）。

**硬规则**：标题为空时**绝不**用笔记编号顶替。
实在取不到就让模板里那一段留空（渲染时会连分隔符一起去掉），
面板显示「未命名笔记」—— 难看，但至少不骗人。

### 4.5 交互

- 右下角悬浮按钮（FAB），hover 展开为带文字的胶囊
- 笔记页：面板分「视频」「图片」两段，逐条显示尺寸/时长/大小
- 主页页：卡片网格 + 顶部筛选（全部 / 视频 / 图集）+ 全选/反选 + 底部「下载所选」
- 面板用 Shadow DOM 隔离，不污染小红书自己的样式
- 浅色 / 深色双主题，跟随系统
- `prefers-reduced-motion` 下关闭动效

### 4.5.1 按文件类型筛选下载

**要解决的问题**：批量下载一个创作者的内容时，用户经常只想要视频，或者只想要图片。
现有的「视频 / 图集」页签筛的是**笔记**，不是**文件** —— 一条视频笔记会同时产出
`1.mp4` 和封面 `2.jpg`，光筛笔记挡不住封面。

**语义**：`全部 / 视频 / 图片` 是全部文件的一个**划分**（视频 + 图片 = 全部）。
视频笔记的封面本身就是一个图片项，所以它归「图片」；「只下载视频」时它会被跳过。

**为什么必须是划分而不是「子集」**：如果「只下载图片」不包含封面，
那么「视频 + 图片 ≠ 全部」，用户会发现某些文件在任何筛选下都拿不到 —— 那就是 bug。

**两处界面，含义不同，必须分开**：

| 控件 | 位置 | 作用 |
|---|---|---|
| 笔记类型（全部 / 视频 / 图集） | 主页批量页工具条第一行 | 筛**卡片列表**：看哪些笔记、勾哪些笔记 |
| 下载内容（全部 / 视频 / 图片） | 工具条第二行（笔记页第一行） | 筛**下载的文件**：下哪些文件 |
| 保存结构（按笔记 / 按作者 / 全部平铺） | 工具条第三行（笔记页第二行） | 决定**文件落在哪种目录里**，见 4.4.1 |

这几个都用分段控件，视觉上一样，所以必须各带一个文字标签
（「笔记类型」「下载内容」「保存结构」）区分。
主页页的「下载内容」**不改变卡片列表** —— 它只决定下载哪些文件，
底部会写明「只下载视频文件」，避免用户以为筛了就会少显示几张卡。

**状态存在设置里**（`downloadFilter`）：换页面、关掉面板再打开都还认这个偏好 ——
「我只想存视频」是长期意图，不是一次性操作。设置页也提供同一个开关。

**兜底**：所有下载入口（面板按钮、主页卡片悬停快捷下载）最终都走
`startDownload()`，那里再按筛选过滤一次；批量下载在组装任务时过滤。
被筛掉的文件会明确计数（「已跳过 1 张图片」），不做静默丢弃。

### 4.6 SPA 路由变化不能让面板消失

小红书是 SPA，站点初始化时会调一次 `history.replaceState`，这会触发路由事件。
如果处理不当，面板会被清空重建成骨架屏 —— 用户正要点的下载按钮突然消失，
那就是一次**静默无响应**（最难查的那类失败，E2E 上表现为「新增 0 个文件」）。

三处配合才能根治：

1. **路径守卫**：路径没变就不重跑识别
2. **保留旧内容**：重新识别的是同一篇笔记时，保留上一次的结果，不清空
3. **骨架屏只在没有旧内容时显示**：否则按钮会凭空消失

## 5. 已知限制（如实告知，不假装没有）

1. **主页批量下载需要登录小红书**。游客态服务端不下发笔记 id，页面里的链接只有 `/explore/`。
   插件会明确显示「小红书在未登录状态下不返回笔记 id（这个账号能看到 N 张卡片，但拿不到内容地址）」并给登录入口。
   这一步**不等滚动扫描跑完**（默认 40 轮 ≈ 28 秒）才提示 —— 页面上已经有卡片却拿不到 id，
   再滚也不会有 id，所以立刻说明。
2. **直链有效期约 2 小时**，过期后需要重新识别。
3. 只支持小红书网页端，不支持 App 独占内容。
4. 笔记封面（视频笔记的 `imageList`）会作为一个图片项一并提供。
   按文件类型筛选时它算**图片**：「只下载视频」会跳过它，
   「只下载图片」则会包含它 —— 这样「视频 + 图片 = 全部」，不会有文件落在筛选之外。
5. **不支持 rednote.com（国际版）**。实测该站所有页面强制跳登录，游客态无法验证笔记结构，
   与其发一个没验过的版本，不如先不做。
6. **频繁下载原始画质可能触发平台限流**。竞品 RedNote Downloader 在设置里明确提示：
   大量下载原画可能导致账号被要求重新登录并进入 1–3 天冷却期；压缩画质与其它媒体不受影响。
   本产品默认下载原画，所以这个风险存在。
7. **极少数笔记既没有标题、也没有可用的正文首行**（实测样本里没遇到过，但理论上存在）。
   这类笔记的文件名里只剩序号，面板显示「未命名笔记」——
   宁可难看，也不用编号冒充标题。
8. **打包模式要多等一会儿**：文件要先收齐再打成包，界面上的进度条走的是「打包进度」，
   不是「下载进度」—— 包没打好之前，磁盘上还没有东西。
9. **打包模式下的单文件重试会单独打一个 `-补` 的小包**，不影响已经下好的那个包。
10. **打包模式下没有断点续传**：中途失败只能整个重下。
11. **打包模式下后台页面被浏览器回收了任务就没了**（扩展重载、浏览器退出）——
    SW 重启时对账发现后台页面不在，就把在途条目标失败让用户重试。

**结论与本产品的定位**：

- 品类有真实需求，但头部也就 2 万用户 —— 说明**「能用」不构成壁垒，体验才是**
- **14 个扩展里 0 个用浏览器角标或侧边栏做进度反馈**，进度最完整的也只有 `6/9` 一个数字
- **最强的那款（2 万用户、83 条评）的主页批量选择至今没实现**（其仓库 TODO 明确列为未完成项）——
  本产品的「网格勾选 → 分篇建目录 → 逐文件进度」是这个品类里的空白
- 全行业的通病是**静默失败**：「10 张图下了 7 张」这个事实没有一家会告诉用户
- 隐私是空白区：多数竞品把解析请求发往自家服务器（`api.old-panda.com` / `geckoinfo.cloud`），
  头部产品还硬编码了 Google Analytics。本产品**全本地处理、零遥测**

## 7. 验证方式

| 层次 | 手段 | 现状 |
|---|---|---|
| 纯逻辑 | `pnpm test`（87 个用例）：CDN 规则、文件名规则、提取逻辑、笔记 id 精确匹配、文件类型筛选的划分性质、标题兜底链、保存结构与三套模板、旧设置迁移、下载队列（重试 / 0 字节 / SW 重启自愈）、ZIP 写入器（按规范解析字节，交叉验 CRC）、`__INITIAL_STATE__` 容错解析（JS 字面量 / `undefined` / `NaN` / `-Infinity`） | 全绿 |
| 端到端 | `scripts/e2e.mjs`：真实 Chrome 加载扩展 → 打开笔记页 → 识别 → 校验标题不是编号 → 点下载 → 校验落盘文件 → 切换文件类型筛选 → 切换三种保存结构 → 打开作者主页 → 校验游客态的登录提示 | 真站点现在对未登录访问跳 `/login`，脚本会明确提示这一点 |
| 端到端（批量） | `scripts/e2e-batch.mjs`：本地假站点（形状照抄真实响应，含 JS 字面量状态与「SSR 无详情」形态）→ 扫描 → 勾选 → 解析 → 下载 → 校验分篇目录 → 切「只下载视频」再下一轮 → 切「按作者」再下一轮（校验文件落在作者目录里）→ 切「全部平铺」再下一轮（校验文件平铺且文件名带作者标题）→ 换成「SSR 里没有详情」的站点再下一轮（校验退回 iframe 兜底、且只多花一两次抓取）→ 校验拿不到媒体的笔记标成「未取到资源」→ **换成「SSR 直链是坏的」的站点再下一轮（校验下的是页面那份好的直链，不是 SSR 那条 404）** | 36/36 通过 |
| 端到端（打包） | `scripts/e2e-zip.mjs`：切到打包模式 → 批量下载 → 校验**只有 1 条浏览器下载记录** → 校验磁盘上只有 1 个 zip → 用 Python `zipfile` 与 macOS `ditto -x -k` 交叉验证包内结构与字节 → 校验解析主路是隐藏 iframe、笔记页只抓一次 → 校验面板不再提「选目录」 | 17/17 通过 |
| 规模实测 | `scripts/probe-scale.mjs`：300 个视频，浏览器下载 vs 打包成 zip 对比（下载记录数 / 落盘文件数 / 总耗时 / storage 写盘 / iframe 数）；第 5 个参数传 `nos` 可模拟「SSR 里没有详情」的最坏情况 | 见 4.3.2 的表 |
| 规则实测 | `scripts/probe-filenames.mjs`（逐字符扫文件名）、`scripts/probe-dnr.mjs`（DNR 对 SW 下载是否生效） | 结论已写进实现 |
| 线上实测 | Playwright 勘察真实小红书：推荐流 193 条卡片、笔记详情 158 篇，确认 `title` 为空串的那一类笔记、`desc` 首行就是标题、`user.notes` 是「5 tab × 数组」的双层结构 | 结论已写进实现 |
| 人工 | 加载 `dist/` 到日常浏览器，用已登录的小红书账号走一遍主页批量；顺便看一眼**登录态下笔记页的 SSR 里到底有没有笔记详情**（决定快路能不能走通） | 待用户验收（需要登录态） |

## 8. 留给后续

- 图片原图模式下的并发下载需要单独限速（大图并发容易触发 CDN 限流）
- 批量下载完成后生成一个 `index.csv` / `index.md` 清单（作者、标题、原链接、文件名）
- 记住「按作者 + 标题」去重，避免重复下载同一篇笔记（**竞品全线空白**，值得做）
- 下载历史 / 任务总览页（竞品最强的那款也没有）
- 支持 `rednote.com`（国际版）—— 需要一个已登录的红书账号才能验证笔记结构
- 验证码 / 风控提示（小红书要求验证码时，现在只能靠用户自己看出来）
- Edge 商店上架（manifest 已兼容，仅需换商店素材）
- 打包成 `.zip` 提交 Chrome Web Store（权限已收敛到 3 个，审核风险低）
- 用 `chrome.alarms` 替代 `setInterval` 轮询（MV3 里 SW 存活时间受限，轮询不是长任务）
